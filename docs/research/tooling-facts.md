## 2. Expo in a pnpm and Turborepo monorepo

## 7. Hermes and Intl

**The Hermes build pinned by React Native 0.88.1 lacks exact decimal-string NumberFormat.** NumberFormat `formatToParts` is enabled on Android and omitted on Apple. DateTimeFormat supports named time zones on both platforms. [React Native engine pin](https://github.com/react/react-native/blob/v0.88.1/packages/react-native/sdks/.hermesv1version) · [Hermes NumberFormat](https://github.com/meta/hermes/blob/hermes-v260318099.0.5/lib/VM/JSLib/Intl.cpp#L1290-L1429) · [Apple date formatter](https://github.com/meta/hermes/blob/hermes-v260318099.0.5/lib/Platform/Intl/PlatformIntlApple.mm#L1459-L1486) · [Android date formatter](https://github.com/meta/hermes/blob/hermes-v260318099.0.5/lib/Platform/Intl/java/com/facebook/hermes/intl/DateTimeFormat.java#L273-L279)

- **Decimal strings.** In `hermes-v260318099.0.5`, `format("187.425")` first coerces the string to binary64 via `toNumber_RJS`. It can produce the expected text for a given precision, but that result does not establish exact decimal-string handling. The ECMA-402 v3 path uses `ToIntlMathematicalValue` to preserve the mathematical value of the string before applying formatting options. Android NumberFormat `formatToParts` also uses `toNumber_RJS`. [Pinned Hermes implementation](https://github.com/meta/hermes/blob/hermes-v260318099.0.5/lib/VM/JSLib/Intl.cpp#L1349-L1429) · [ECMA-402, June 2026](https://402.ecma-international.org/13.0/#sec-tointlmathematicalvalue)
- **Time zone.** `Intl.DateTimeFormat("en-US", { timeZone: "America/New_York" })` uses the OS time-zone data on both platforms. Apple passes the requested zone to `NSTimeZone`. Android resolves it and sets the formatter zone through ICU. Source supports the normal IANA identifier. Exact output on particular iOS or Android versions is **unverified**. [Apple formatter](https://github.com/meta/hermes/blob/hermes-v260318099.0.5/lib/Platform/Intl/PlatformIntlApple.mm#L1784-L1787) · [Android ICU formatter](https://github.com/meta/hermes/blob/hermes-v260318099.0.5/lib/Platform/Intl/java/com/facebook/hermes/intl/PlatformDateTimeFormatterICU.java#L391-L393)

## 8. Alpaca Basic stock market data

**Basic gives free real-time IEX data, up to 30 WebSocket symbols, and 200 historical REST requests per minute.** Plan for one active stream per endpoint. Historical SIP is available with a 15-minute cutoff. [Basic plan](https://docs.alpaca.markets/us/docs/about-market-data-api) · [Connection limits](https://docs.alpaca.markets/us/docs/streaming-market-data) · [Market Data FAQ](https://docs.alpaca.markets/us/docs/market-data-faq)

- **Feed and connection.** Use `wss://stream.data.alpaca.markets/v2/iex` for live Basic equity data. The limit of one active connection is per user and endpoint for most subscriptions, with error **406** when exceeded. Real-time SIP requires the appropriate subscription. The stock stream docs list `v2/delayed_sip`, but Basic access to that WebSocket endpoint is **unverified** here. [Stock stream feeds](https://docs.alpaca.markets/us/docs/real-time-stock-pricing-data) · [Connection and error docs](https://docs.alpaca.markets/us/docs/streaming-market-data) · [Basic plan](https://docs.alpaca.markets/us/docs/about-market-data-api)
- **History and recent bars.** The plan lists US equity and ETF history since **2016**. For `GET /v2/stocks/bars`, specify `feed=iex` for recent data or `feed=sip` with `end` at least 15 minutes old. The bars API defaults the end time to now when you have real-time access to the selected feed, and to now minus 15 minutes otherwise. The latest and snapshot endpoints require a SIP subscription when queried with `feed=sip`. [Plan and history](https://docs.alpaca.markets/us/docs/about-market-data-api) · [Historical bars API](https://docs.alpaca.markets/us/reference/stockbars) · [SIP entitlement FAQ](https://docs.alpaca.markets/us/docs/market-data-faq)

Use the paper Trading API key and secret against `data.alpaca.markets` for historical REST or `stream.data.alpaca.markets` for the stream. Account-specific entitlements and a live authenticated request are **unverified**. ## 9. Node WebSocket server and backpressure

**`ws` 8.23.0 is an established server dependency.** Node 26 has a built-in WebSocket client and requires a library for a WebSocket server. Fastify exposes the raw socket directly and Hono exposes it as `ctx.raw`. [ws npm metadata](https://registry.npmjs.org/ws) · [Node v26.13.1 WebSocket API](https://nodejs.org/download/release/v26.13.1/docs/api/globals.html#websocket) · [Node client and server guidance](https://nodejs.org/learn/getting-started/websocket#important-to-understand) · [Fastify plugin](https://github.com/fastify/fastify-websocket) · [Hono adapter source](https://github.com/honojs/node-server/blob/v2.1.11/src/websocket.ts#L326-L341)

- **ws** 8.23.0, 2026-11-12, exports `WebSocketServer` and documents `websocket.bufferedAmount` as bytes queued for transmission. Node's browser-compatible global client has been stable since v22.4.0. [ws npm metadata](https://registry.npmjs.org/ws) · [ws API](https://github.com/websockets/ws/blob/8.23.0/doc/ws.md#websocketbufferedamount) · [Node globals](https://nodejs.org/download/release/v26.13.1/docs/api/globals.html#websocket)
- **Fastify** `@fastify/websocket` 11.3.7, 2026-11-04, types the route handler's first argument as the actual `ws.WebSocket`. Read `socket.bufferedAmount` directly. [npm metadata](https://registry.npmjs.org/@fastify%2fwebsocket) · [Pinned handler type](https://github.com/fastify/fastify-websocket/blob/v11.3.7/types/index.d.ts#L98-L105)
- **Hono** `@hono/node-server` 2.1.11, 2026-11-20, accepts a supplied `ws.WebSocketServer`. Its helper passes the socket as `ctx.raw`. The wrapper itself has no `bufferedAmount` and its `WebSocketLike` type omits the property. Narrow `ctx.raw` to `ws.WebSocket` to read it in TypeScript. The older `@hono/node-ws` 1.3.2, 2026-11-21, is deprecated in favor of the Node adapter helper. [Node adapter npm metadata](https://registry.npmjs.org/@hono%2fnode-server) · [Adapter setup](https://github.com/honojs/node-server#websocket) · [Pinned raw socket mapping](https://github.com/honojs/node-server/blob/v2.1.11/src/websocket.ts#L326-L341) · [Pinned socket interface](https://github.com/honojs/node-server/blob/v2.1.11/src/websocket-types.ts) · [Deprecation notice](https://github.com/honojs/middleware/blob/@hono/node-ws@1.3.2/packages/node-ws/README.md) · [Legacy package date](https://registry.npmjs.org/@hono%2fnode-ws)
- A local Node **26.12.0** handshake probe observed numeric `bufferedAmount` on the Fastify socket and Hono's `ctx.raw`, and `undefined` on the Hono wrapper. This checked access to the property. Backpressure behavior under a slow consumer is **unverified**. ### 7. App Router server prefetch and store lifetime

**Prefetch in a Server Component and pass the dehydrated queries through `HydrationBoundary`. Scope request-specific stores to their client provider instance.** [TanStack App Router guide](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr) · [Zustand Next.js guide](https://zustand.docs.pmnd.rs/learn/guides/nextjs)

- In an async page, layout, or nested Server Component, create a fresh `QueryClient`, await `prefetchQuery`, and wrap the consuming components in `<HydrationBoundary state={dehydrate(queryClient)}>`. Use the same query key in the client `useQuery` and set a positive `staleTime` to avoid an immediate refetch. A request-scoped React `cache(() => new QueryClient())` can share a prefetch client across Server Components. Each dehydration of that client serializes its eligible queries again. [Prefetching](https://tanstack.com/query/latest/docs/framework/react/guides/prefetching) · [App Router hydration and request-scoped cache](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr)
- Mount a `'use client'` `QueryClientProvider` from the layout. TanStack recommends a fresh client on the server and a reusable browser client so initial suspension can preserve the cache. For a mutable Zustand store, create it once per provider with lazy `useState`. Keep the factory and context at module scope and the store instance inside the provider. Seed server rendering and browser hydration with the same data. Zustand assigns store access to Client Components. A local React server-render probe with two concurrent renders and Query 5.108.4 produced the correct distinct prefetched values and provider state. Full App Router hydration is **unverified**. [TanStack provider setup](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr#initial-setup) · [Next.js context providers](https://nextjs.org/docs/app/getting-started/server-and-client-components#context-providers) · [Zustand provider setup](https://zustand.docs.pmnd.rs/learn/guides/nextjs) · [Query 5.108.4](https://registry.npmjs.org/%40tanstack%2Freact-query/5.108.4)
